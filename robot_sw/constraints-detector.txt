# constraints-detector.txt — the pip half of the app image, fully pinned.
#
# WHY THIS FILE EXISTS (measured 2026-09-01):
#   `pip install ultralytics` does NOT respect a torch pin that was installed before it.
#   Resolution of `ultralytics==8.4.136` on this base image, with NOTHING pre-installed,
#   pulls **torch 2.13.0 (CUDA build) + triton + 16 nvidia-* wheels** (measured with
#   `pip install --dry-run --report`). That is several GB of CUDA runtime inside a
#   container that runs its detector on CPU by design and is given no GPU.
#   Installing the CPU wheels first is NOT enough by itself — torchvision from PyPI is
#   the CUDA build and drags a matching CUDA torch back in. This file is what makes the
#   pin stick, and the Dockerfile turns it into a build-time assertion (a CUDA torch
#   fails the build, it does not merely warn).
#
# The numpy pin is a second, separate trap: unconstrained, pip installs numpy 2.5.2 into
# /usr/local and it SHADOWS the distro numpy 1.26.4 that every ROS 2 Jazzy C extension on
# this image was built against. Pinning to the distro version means pip resolves
# "already satisfied" and installs nothing (which is also why opencv-python backtracks
# from 5.0.0.93 to 4.11.0.86 — the last release that accepts numpy 1.x).
# setuptools is pinned for the same reason: colcon's ament_python build runs setup.py
# with the distro setuptools (68.1.2); a pip-installed newer one would shadow it.
#
# HOW TO REGENERATE (do not hand-edit versions):
#   1. build the image without `-c` on the two pip layers,
#   2. `docker run --rm <img> python3 -c "from importlib.metadata import distributions;
#      [print(f'{d.metadata[\"Name\"]}=={d.version}') for d in distributions()
#       if str(d._path).startswith('/usr/local/')]"` (= the pip-installed set only),
#   3. paste the sorted result below and re-add the two distro guards at the bottom.
#
# Measured 2026-09-01 on ros:jazzy-ros-base-noble@sha256:31daab66… (python 3.12.3).
